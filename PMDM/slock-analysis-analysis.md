## 内容摘要
本文件是一份关于 **Slock.ai** 平台的深度技术与产品分析报告。Slock.ai 被定义为一个 **AI-Native（AI原生）** 的协作平台，核心理念是让人类与 AI Agent 作为平等的一等公民进行协作。

报告详细剖析了 Slock.ai 的混合架构设计（云端平台 + 本地 Agent 运行时）、基于 MCP 协议的集成机制、独特的“消息即任务”管理模式以及 Agent 的生命周期与记忆持久化方案（MEMORY.md）。通过与 Slack、Microsoft Teams 等竞品的对比，指出了其在本地化执行能力和深度人机协作流程上的创新，同时也揭示了当前在文件支持和生态方面的局限性。

## 关键内容

### 1. 产品定位与核心理念
- **定义**：专为人类与 AI Agent 协作设计的即时通讯与任务管理平台。
- **差异化**：不是传统的 IM 工具加 AI Bot，而是从底层将 Agent 视为拥有同等身份和权限的“一等公民”。

### 2. 系统架构特征 (Hybrid Architecture)
- **云端层**：负责 Web App 展示、API 网关、消息代理及数据存储（频道、消息、任务）。
- **本地层**：Agent（如 Claude Code）运行在用户本地机器，拥有独立的文件系统工作区 (`~/.slock/agents/{uuid}/`)。
- **通信协议**：通过 **MCP (Model Context Protocol)** 桥接云端与本地，包含 11 个核心工具（如 `send_message`, `claim_tasks`, `upload_file`）。

### 3. 核心功能模块
- **任务管理系统**：
    - 实现了 **“消息即任务”** 的融合模型，顶层消息可直接转化为任务。
    - 工作流状态：`todo → in_progress → in_review → done`。
    - 引入 **Claim（认领）机制**，利用乐观锁思想防止多 Agent 并发冲突。
- **Agent 生命周期**：
    - 采用 **Start/Sleep/Wake** 循环，非持续运行以节省资源。
    - **记忆持久化**：依赖本地 `MEMORY.md` 和 `notes/` 目录恢复上下文，支持跨会话知识积累。
- **UI 结构**：包含标准的 Channel/DM/Thread 视图，以及集成的 Task Board（看板）和 Agent 状态指示器。

### 4. 技术亮点
- **本地执行能力**：Agent 可直接操作本地代码仓库、运行命令行，解决了纯云端 Bot 无法触及用户私有环境的痛点。
- **Human-in-the-loop**：任务完成需经过 `in_review` 状态由人工确认，确保安全性。

## 分析与建议

### 1. 架构优势评估
- **隐私与权限**：Agent 本地运行的架构极具前瞻性。它允许 AI 处理敏感代码库而无需上传至云端，非常适合开发者和注重数据安全的团队。
- **轻量级集成**：仅用 11 个 MCP 工具就覆盖了完整的协作闭环，降低了 Agent 开发的复杂度，提高了系统的稳定性。

### 2. 潜在风险与局限
- **资源消耗**：每个 Agent 在本地独立运行并维护完整的代码仓库副本，对于配置较低的客户端机器可能造成性能压力。
- **单点依赖**：目前高度依赖 Claude Code 作为运行时，且缺乏复杂的 RBAC（基于角色的访问控制）模型，可能限制其向大型企业推广。
- **功能缺失**：不支持视频/语音通话，且文件支持仅限于图片（<5MB），限制了多媒体协作场景。

### 3. 改进建议
- **增强文件处理能力**：建议尽快支持文档（PDF, Word）和代码文件的直接解析与预览，而不仅仅是作为附件上传。
- **完善搜索与归档**：鉴于“记忆”的重要性，应增加全局历史搜索功能和智能摘要归档，辅助 Agent 更高效地检索上下文。
- **扩展运行时支持**：除了 Claude Code，建议抽象出通用的 Agent 接口标准，以便兼容其他主流 LLM 运行时（如 LangChain, AutoGen 等）。
- **引入细粒度权限**：随着团队规模扩大，需要增加频道级别的 Agent 权限控制（例如限制某些 Agent 只能读取不能发送）。
